# Turing Tester: SpeechJudge-Based TTS Evaluation and Improvement Environment

**Purpose of this document:** A detailed record of the idea, technical discussion, alternatives, decisions, recommended plan, benchmark design, and implementation caveats discussed for the hackathon project.

**Scope:** This document covers the conversation from the original idea of AI-vs-human voice detection through the final Turing Tester / SpeechJudge / DPO discussion. It intentionally excludes the later discussion about other companies and business models.

**Working project name:** Turing Tester (name is provisional)

**Primary goal:** Build a hackathon prototype that evaluates synthetic speech, identifies recurring quality weaknesses, uses an existing learned speech-quality judge to guide post-training of a small text-to-speech (TTS) model, and measures whether the updated model actually improves.

---

## Executive summary

The initial thought was to build software that detects whether an uploaded voice is AI-generated or human. After clarification, the actual idea became much more specific and useful for a TTS-model development workflow:

> A voice lab submits audio generated by its TTS model. The platform evaluates how human and natural the speech sounds, identifies areas that could improve, and helps the lab run repeated training/evaluation cycles until the model improves.

The product is not primarily an AI-voice detector or a deepfake detector. It is a **TTS evaluation, diagnosis, and model-improvement environment**.

The central technical asset is **SpeechJudge**, a published research project that includes a human-labelled speech-preference dataset, a benchmark for speech-naturalness judgments, and a pretrained generative reward model (SpeechJudge-GRM). The existing model can compare two speech outputs and return quantitative ratings and a textual analysis. It is not designed primarily as an absolute-quality grader for one isolated recording.

For the hackathon, the recommended approach is:

1. Reuse the existing SpeechJudge-GRM checkpoint rather than training a judge from scratch.
2. Use a small TTS model, ideally Qwen2.5-0.5B-TTS for the closest connection to the paper's own downstream experiment.
3. Generate several speech candidates for the same prompt and use SpeechJudge to compare candidates.
4. Convert the comparisons into preferred/rejected pairs and use an online preference-optimization loop (the paper uses online DPO) to update the TTS model.
5. Evaluate the original and updated model on the exact same locked set of held-out prompts, using consistent conditions.
6. Report SpeechJudge preference results separately from human-listener results, text accuracy, and speaker similarity.
7. Build a visible user workflow: baseline voice → diagnostic feedback → training loop → updated voice → benchmark comparison.

This is realistic as a scoped proof of concept, but implementation effort depends on whether the exact TTS model and training code can expose the required token sequences/log probabilities and support DPO. Reusing SpeechJudge does not automatically make training integration trivial.

A technically accurate description of the project is:

> **An AI-feedback-driven TTS evaluation and online preference-optimization environment that helps voice-model developers diagnose speech-quality weaknesses, update a supported TTS model, and measure improvements on held-out tests.**

## 1. How the idea evolved

### 1.1 Initial concept: detect AI-generated vs human voice

The first formulation was a software tool that detects whether a voice is AI-generated or human. This could be approached as a binary classification task, but it is a crowded and difficult problem: modern speech can be highly realistic, recording conditions vary, and detectors may fail on generators that were not represented in training.

### 1.2 Clarification: the real goal is to improve TTS models

The intended product is not merely a detector. The user clarified that labs would submit speech generated by their own models and expect the software to act as a grader or benchmark. It should:

- Listen to generated speech.
- Evaluate how natural or human-like it sounds.
- Identify particular weaknesses.
- Give actionable feedback.
- Let the lab update its model or settings.
- Evaluate the improved output again.
- Repeat the process so the lab can see whether it is making progress.

This is closer to a **reward-model-driven evaluation and post-training environment** than an AI-vs-human detector.

### 1.3 Input assumptions

For the hackathon prototype, audio is expected to be uploaded as a clean MP3 rather than captured from a live call or a compressed telephone stream. That removes several robustness challenges from the initial scope, such as telephony compression and real-time latency constraints.

However, MP3 format does not remove all audio-processing concerns. The service still needs to decode audio consistently, handle sample rates and duration, check for corrupted or silent files, and convert audio into the format required by the evaluator and TTS-training pipeline.

### 1.4 Intended users

The initial target is TTS labs or developers who want to improve the speech generated by a model. A relevant future use case is a voice-agent platform such as Bolna, where voice quality, pronunciation, latency, consistency, and language support can affect the quality of calls. The first hackathon implementation should remain narrow and demonstrate the training loop on one supported open model.

## 2. Product definition: Turing Tester

Turing Tester is the working name for a platform that helps a lab answer four questions:

1. **How good is the model right now?**
2. **What kinds of speech quality problems does it exhibit?**
3. **What training signal or examples can help improve it?**
4. **Did the updated model actually get better on independent tests?**

### 2.1 Proposed product components

#### A. Model connector

Allows a user to select or connect a supported TTS model. For the initial prototype, the model is a locally or cloud-hosted open TTS model. A closed API can be evaluated if its terms permit the intended use, but its internal weights generally cannot be modified unless the provider offers a supported fine-tuning or training interface.

The connector should keep track of:

- Model name and checkpoint/version.
- Model configuration and generation parameters.
- Text prompt.
- Speaker reference, if required.
- Desired style or delivery instruction, if supported.
- Output audio and metadata.

#### B. Evaluation engine

Generates or receives audio and runs the evaluation process. The main grader is SpeechJudge-GRM, initially used for pairwise comparison. Other checks can be added for text correctness, audio quality and speaker consistency.

#### C. Diagnostics and failure analysis

Collects the outputs of the evaluator and supporting tools, then summarizes recurring issues. Potential categories include:

- Monotonous or contextually inappropriate intonation.
- Unnatural pauses or phrase timing.
- Mechanical rhythm or syllable duration.
- Mispronounced words or phonemes.
- Missing, added or altered words.
- Insufficient or inappropriate expressiveness.
- Inconsistent speaker identity.
- Audio artifacts, excessive breathiness, buzziness, metallic sound, or other quality defects.

These should be treated as categories to investigate and validate, not as labels that the first version can identify perfectly. A textual explanation from a judge is evidence/hypothesis, not guaranteed proof of the underlying cause.

#### D. Training environment

For supported open models, produces candidates, derives preference signals, runs the training update and saves checkpoints. The first target is online preference optimization using SpeechJudge as the evaluator/reward source.

#### E. Benchmark and version tracker

Tracks the base checkpoint, each trained checkpoint, generated audio, evaluator results, human assessments where available, training configuration, and benchmark performance. It should make model changes reproducible and show the difference between versions.

#### F. Data recommendations (stretch feature)

Summarizes recurring failures and recommends the kinds of additional examples or human judgments that would be useful. For example, it might request more comparisons involving conversational emphasis, long sentences, a particular language, or a specific speaking style.

This feature must not pretend that a reward model's explanation alone proves which dataset will fix the failure. Recommendations should be hypotheses to test, and human preferences may be needed where the judge is uncertain.

## 3. SpeechJudge: what it provides

### 3.1 The research project

SpeechJudge: *Towards Human-Level Judgment for Speech Naturalness* (arXiv:2511.07931; published at ICLR 2026) introduces three related resources:

1. **SpeechJudge-Data:** a corpus of approximately 99,000 annotated speech pairs.
2. **SpeechJudge-Eval:** a benchmark for evaluating how well a system predicts human speech-naturalness preferences.
3. **SpeechJudge-GRM:** a generative reward model trained to judge speech naturalness.

Official links:

- Paper: https://arxiv.org/abs/2511.07931
- Conference entry: https://proceedings.iclr.cc/paper_files/paper/2026/hash/8acd02d0c55edc3b47a7f9aa42b9cfae-Abstract-Conference.html
- Official repository: https://github.com/AmphionTeam/SpeechJudge
- Reward-model checkpoint: https://huggingface.co/RMSnow/SpeechJudge-GRM
- Dataset: https://huggingface.co/datasets/RMSnow/SpeechJudge-Data
- Project page: https://speechjudge.github.io/

### 3.2 What is in the dataset?

SpeechJudge-Data is not 99,000 perfect single voice recordings. It is a **human-labelled corpus of speech pairs**. The data includes two generated speech candidates for a text, along with human annotations about intelligibility/text accuracy and relative naturalness preference.

The authors describe collecting annotations from 69 annotators over two months, with each pair receiving an average of 2.49 annotations. The data uses synthesized speech from several TTS models and includes multiple speech styles and multiple languages. The primary reported languages include English and Chinese, with code-switching/cross-lingual cases in the data construction.

This structure makes the dataset particularly suitable for preference-based training and reward-model evaluation. It does not directly provide timestamped annotations for every naturalness defect, such as exactly where a pause sounds awkward.

Before training, inspect the current Hugging Face dataset card and actual split metadata. Split names, counts, file sizes and formats should be read from the version downloaded rather than hard-coded from memory. The earlier discussion used approximately 42,000 training pairs as a planning estimate; verify the current configuration and exact counts before starting.

### 3.3 What does the reward model do?

SpeechJudge-GRM is based on Qwen2.5-Omni-7B and was trained on SpeechJudge-Data using a two-stage method:

1. Supervised fine-tuning (SFT) with generated reasoning/explanations.
2. Reinforcement learning with GRPO on challenging examples.

It is designed to compare two speech outputs and produce scores and a textual analysis of relative naturalness. The repository exposes a function called `compare_wavs()` that takes the target text and two audio paths. The example returns a score for output A, a score for output B, and a detailed analysis.

The key practical detail is that its documented interface is **pairwise comparison**, not a fully calibrated absolute score for a single recording. If the product accepts only one uploaded MP3, it needs a comparison target or a separately validated single-sample quality estimator.

### 3.4 Reported benchmark results

The paper reports approximately:

- SpeechJudge-GRM: 77.2% accuracy on SpeechJudge-Eval.
- With inference-time voting/scaling over 10 judgments: 79.4%.
- A Bradley–Terry-style reward-model baseline: 72.7% overall.

These numbers measure how well the judge predicts human preferences on the paper's benchmark. They do **not** mean that every voice quality score is 77.2% accurate, and they do not mean a TTS model has 77.2% naturalness.

The expressive-speech subset is harder than ordinary speech. Performance can vary by language, style, generator, prompt, speaker reference and audio conditions. The reward model may also make mistakes or be exploited when a generator learns to maximize its scores.

### 3.5 Use the reward model before retraining it

Recommended first step: run the released checkpoint and test the official example. Do not begin by retraining the reward model itself. The checkpoint already represents a substantial investment in human-labelled speech preferences.

Official repository usage is documented around:

```python
from infer.main_grm import load_model, compare_wavs

model_path = "pretrained/SpeechJudge-GRM"
model, processor = load_model(model_path)

target_text = "Your target text here"
wav_path_a = "path/to/audio_a.wav"
wav_path_b = "path/to/audio_b.wav"

rating, result = compare_wavs(
    processor, model, target_text, wav_path_a, wav_path_b
)

print("Output A score:", rating["output_a"])
print("Output B score:", rating["output_b"])
print(result)
```

Treat this as a description of the documented interface rather than a guarantee that the code will run unchanged in every environment. Follow the current repository's requirements and examples.

### 3.6 Licensing and compute cautions

The SpeechJudge-GRM checkpoint and dataset are marked **CC BY-NC 4.0** in their hosted materials. That license includes noncommercial restrictions. Do not assume that the assets can be used in a commercial product just because they are publicly downloadable. Review the exact license, attribution requirements, dataset terms and hackathon rules. For a commercialized service, obtain appropriate permissions or identify assets with terms that allow the intended use.

The model checkpoint is large (the Hugging Face listing shows approximately 22.4 GB of checkpoint files and an 11B-parameter model). A GPU with 12 GB VRAM is unlikely to run the full model in normal precision without offloading/quantization or another suitable deployment arrangement. The TTS model training and the judge inference may need separate jobs or separate GPUs. Profile actual VRAM and runtime before choosing a full experimental workload.

## 4. Core learning concepts

### 4.1 SFT: Supervised Fine-Tuning

SFT teaches a model by providing input/output examples of the behavior to learn.

For a TTS model:

- **Input:** target text, speaker reference and style conditions, depending on the architecture.
- **Target:** the actual target speech representation/audio corresponding to that input.

The target is the teacher's **audio output**, encoded in the format required by the TTS model's training pipeline. A critique such as “the voice needs more expressive emphasis” is not, by itself, an SFT audio target. You would need to generate a suitable audio example, verify it, and pair that audio with the correct text, speaker reference and style metadata.

SFT can teach a smaller TTS model to imitate the examples it sees, but it depends on the quality, diversity and compatibility of the demonstration data. A stronger teacher may generate better examples, but only use a provider's generated audio for training if the applicable terms expressly permit that use. In the earlier discussion, ElevenLabs was raised as a possible teacher; its usage restrictions may prohibit using its output to train or improve another model unless expressly permitted. Check the current terms or use a teacher whose licence clearly allows the intended training use.

### 4.2 Preference learning

Instead of showing only one target, preference data says which of two outputs is better.

Example:

- Prompt: “I would be happy to help you with that.”
- Candidate A: natural emphasis and pauses.
- Candidate B: flatter, more mechanical delivery.
- Preferred: Candidate A.

That preference can support training methods such as DPO or can train a reward model.

### 4.3 DPO: Direct Preference Optimization

DPO stands for **Direct Preference Optimization**. It is an optimization method that trains a model to favor preferred outputs over rejected outputs using preference pairs and a reference policy. It does not require fitting a new reward model specifically for the DPO algorithm, although a reward model such as SpeechJudge can supply the preference labels.

DPO is not the same thing as conventional policy-gradient reinforcement learning. It is a preference-optimization method. If candidate samples are generated during the optimization process and then converted into new preference pairs, this can be described as **online preference optimization**. The project can be broadly described as an RL-style or AI-feedback-driven training environment, but the technical method in the recommended implementation is online DPO, not necessarily policy-gradient RL.

### 4.4 RL and reward models

In conventional RLHF (Reinforcement Learning from Human Feedback), humans commonly judge model outputs. Their preferences may be used to train a reward model, and that reward model then grades further outputs. The generation model is then optimized using the reward signal.

Turing Tester can reuse an already-trained reward model. This means humans do not have to grade every new candidate during every iteration. SpeechJudge supplies an **AI approximation of human preference** based on human-labelled data it has already learned from.

This is not the elimination of human judgment. It is the reuse of previous human judgments through a learned grader. The grader can be wrong, particularly on new languages, unusual speaking styles or outputs unlike its training data. Independent human evaluation remains important to verify real progress and detect reward hacking.

### 4.5 SFT, offline DPO, online DPO and policy-gradient RL: differences

| Method | Training signal | Does the model generate candidates during the training loop? | Main benefit | Main risk/limitation |
|---|---|---|---|---|
| SFT on teacher audio | A demonstrated target audio output | Not inherently | Straightforward imitation learning | Can copy teacher limitations; requires compatible high-quality target audio |
| Offline DPO | Fixed preferred/rejected pairs | Not necessary during each update | Directly reuses existing preference datasets | Optimizes within the coverage of the supplied preference data |
| Online DPO | Freshly generated candidates converted into preferences | Yes | Can learn from current-model outputs | More expensive and can exploit the judge |
| Policy-gradient RL (e.g., a suitable GRPO/PPO-style method) | Rewards for sampled outputs/sequences | Yes | Can optimize directly against a reward signal | More complex, more sensitive to implementation and reward design |
| SFT followed by DPO | Demonstrations then preferences | Depends on second stage | SFT provides a starting behavior; preference training refines it | More moving parts and requires both training paths |

For the hackathon, online DPO is recommended because it closely follows the SpeechJudge paper's TTS post-training example and showcases an automated feedback loop. SFT can be added later as a comparison or warm-up stage, but the first demo should not try to implement every method.

## 5. What the SpeechJudge paper already demonstrates

The paper is particularly relevant because it does more than build an evaluator. It also demonstrates using SpeechJudge-GRM as a reward function for post-training a small TTS model.

In the paper's downstream experiment, the base model is Qwen2.5-0.5B-TTS. The authors test several alignment methods, including offline DPO with SpeechJudge-Data, offline DPO using SpeechJudge-GRM-generated preference labels, and online DPO using SpeechJudge-GRM as the reward function. The TTS model used for the downstream experiment was not involved in constructing SpeechJudge-Data.

Reported results include:

| Method | Text accuracy (T-ACC) | Naturalness CMOS (N-CMOS) |
|---|---:|---:|
| Base Qwen2.5-0.5B-TTS | 84.0% | 0.00 |
| Offline DPO with SpeechJudge-Data | 91.0% | 0.16 ± 0.08 |
| Offline DPO with SpeechJudge-GRM-generated preferences | 91.0% | 0.21 ± 0.12 |
| Online DPO using SpeechJudge-GRM as a reward | 90.0% | 0.25 ± 0.09 |

Interpretation:

- Online DPO achieved the highest reported naturalness improvement among these methods in this experiment.
- Offline methods achieved higher reported text accuracy in the table.
- Naturalness CMOS is a human-listener comparative measure, not a percentage or an absolute naturalness score.
- These results are evidence that the approach can work; they do not prove online DPO always beats SFT or offline DPO for every TTS model.
- The project should not treat the table as a result it has already achieved. It is a prior published result to compare against, not the hackathon's own experimental outcome.

The key lesson is that SpeechJudge is not only a grader; the paper shows it can be used as a reward function that drives updates to a TTS generator. This makes it a strong starting point for Turing Tester.

## 6. Recommended model choice

### 6.1 Closest to the published experiment: Qwen2.5-0.5B-TTS

This should be the first model to investigate if the goal is to reproduce or adapt the published SpeechJudge TTS post-training result. It is small enough to be a plausible experimental base and has already been used in the relevant paper.

Advantages:

- Closely matches the model used in the paper's downstream experiment.
- Reduces the number of unknowns when developing the first training loop.
- Lets the hackathon focus on the evaluation-to-training system rather than inventing an entirely new recipe.

Caveats:

- You still need the correct code path to sample outputs, capture the needed model information and implement compatible DPO updates.
- The fact that the paper trained this model does not imply the official Qwen inference code has a ready-made online-DPO recipe that can simply be turned on.

### 6.2 Alternative: Qwen3-TTS-0.6B-Base

The newer Qwen3-TTS family may be attractive if the team prefers its ecosystem or model quality. But its training format, generation procedure and fine-tuning code may differ. Fine-tuning support for SFT is not automatically support for DPO or RL. A custom preference-training implementation may be needed.

Do not switch model families halfway through the main experiment. Pick one model, establish a baseline, and use that same model in each training and benchmark run.

### 6.3 Practical rule

Use Qwen2.5-0.5B-TTS as the default plan because it is the closest reproduction path. Switch to another TTS model only if the repository or environment cannot be made to support the required training loop within hackathon constraints.

## 7. Recommended training setup

### 7.1 What data should be used?

Use SpeechJudge-Data and SpeechJudge-GRM for different roles:

- **SpeechJudge-GRM checkpoint:** the primary evaluator/reward source.
- **SpeechJudge-Data training split:** an existing human-labelled preference dataset that can support offline training, be used to understand preferences, or supply appropriate prompt/text/reference conditions if they match your experiment.
- **Fresh candidate generations:** provide the online loop with outputs from the current Qwen checkpoint.
- **Held-out benchmark prompts:** reserved for final evaluation, not training or hyperparameter tuning.
- **Human listener labels:** a smaller independent evaluation set to validate that automated improvements correspond to real human preferences.

Do not treat the 99K pair corpus as 99K perfect target audio examples for SFT. It is a preference/annotation dataset. Its labels are more directly suited to preference learning and reward-model evaluation.

### 7.2 Recommended first implementation: online DPO using SpeechJudge

Conceptual loop:

1. Select a training prompt with target text, required speaker reference and style conditions.
2. Ask current Qwen to generate a small number of candidate recordings (for example, 2–4 candidates per prompt).
3. Check the candidates for basic validity and text correctness. Ensure comparison candidates use the same target text and compatible conditions.
4. Use SpeechJudge to compare candidates and choose a preferred/rejected pair.
5. Where possible, filter out cases where one sample is incorrect, corrupted or otherwise incomparable. A voice should not win merely because it omits difficult words or produces a shorter output.
6. Store the chosen/rejected preference pair and the associated TTS training conditions.
7. Update Qwen using a compatible online-DPO implementation.
8. Save the checkpoint and the configuration.
9. Repeat for further training batches.
10. Periodically run the locked benchmark and inspect independent quality measures.

This can be viewed as a model-generated feedback loop. SpeechJudge acts as a learned judge; the DPO implementation actually updates the TTS model.

### 7.3 Don't confuse critique with training signal

SpeechJudge can provide a textual explanation, but the text of a critique is not automatically an optimization objective. For example, “add more pitch variation” does not by itself provide the audio target required for TTS SFT. For preference optimization, the model needs properly represented preferred/rejected outputs or a valid reward applied to the generated output, plus a training algorithm that can update the model.

For the hackathon, use the judge's comparison/reward for training and the explanation for the user-facing diagnosis. Keep those responsibilities separate.

### 7.4 Why not build a full RL system first?

A true policy-gradient RL implementation for speech can involve sampled speech-token sequences, sequence-level rewards, correct log probabilities, reference policy management, careful reward normalization, training stability and protection against reward hacking. It's technically interesting, but adds risk in a time-limited hackathon.

The more achievable route is online DPO, which still demonstrates the key idea that the model repeatedly generates candidates, receives AI feedback, and is updated using that feedback. Describe it accurately as online preference optimization rather than claiming it is the same as policy-gradient RL.

## 8. Benchmark design: how to show the model improved

This is one of the most important parts of the project. The benchmark must test the updated model fairly and must not leak training examples into evaluation.

### 8.1 Use the exact same 500 prompts before and after

The plan discussed is to hold out approximately 500 test prompts and run both model versions on the exact same prompt set:

- Original/base Qwen checkpoint: generate one recording for each prompt.
- Post-trained Qwen checkpoint: generate one recording for each same prompt.
- Compare each pair for the same text and compatible conditions.

Keeping the prompts the same makes the before/after comparison paired. It reduces variation caused by using different prompt sets.

Keep the following fixed where possible:

- Exact target text.
- Speaker reference or voice identity conditions.
- Language and desired speaking style.
- Sampling/generation parameters.
- Audio preprocessing and evaluation settings.

If generation is stochastic, either fix seeds where meaningful or generate enough samples and document the procedure. The same prompt does not guarantee identical stochastic conditions, so record the settings.

### 8.2 Important distinction: two different evaluations

#### Evaluation A: Does SpeechJudge agree with humans?

Use the SpeechJudge-Eval test set (the paper's benchmark) to assess the evaluator's pairwise preference accuracy against human annotations. This tests the grader, not the TTS model's improvement.

#### Evaluation B: Did Qwen improve?

Use a locked set of held-out prompts, generate audio from the base and trained Qwen checkpoints, and ask SpeechJudge to compare each base/trained pair. This estimates whether the reward model prefers the new TTS output.

These tests answer different questions. Do not report evaluator accuracy as though it were the TTS model's naturalness score.

### 8.3 Data leakage precautions

- Do not train or tune the TTS model on the 500 locked prompts.
- Avoid duplicate or near-duplicate target sentences between train and test where practical.
- Do not use the locked benchmark repeatedly to decide hyperparameters or select checkpoints, or it becomes a validation set rather than an untouched test set.
- Keep a separate validation set for development decisions.
- The audio pairs in SpeechJudge-Eval measure the grader's agreement with human preferences. They are not necessarily the same as prompt/audio examples to be used for generating new Qwen benchmark recordings.

If 500 prompts are selected from text associated with the SpeechJudge dataset, ensure the actual text/prompt conditions aren't used for training. Alternatively, write a separate held-out prompt suite and collect independent human judgments for a subset.

### 8.4 Primary win-rate metrics

For each held-out prompt, compare the original Qwen output (A) against the trained Qwen output (B). SpeechJudge may prefer A, prefer B or judge a tie.

Define:

- **Updated-model outright win rate among decisive comparisons:** `updated wins / (updated wins + baseline wins)`.
- **Updated-model win percentage over all prompts:** `updated wins / total prompts`.
- **Tie-adjusted preference score:** `(updated wins + 0.5 × ties) / total prompts`.

Report all three counts clearly instead of hiding ties. A model can have a high conditional win rate while still producing many ties, and a strict win rate over all prompts is a different statistic.

Illustrative example only:

| Outcome | Count |
|---|---:|
| Updated Qwen preferred | 320 |
| Original Qwen preferred | 130 |
| Tie | 50 |
| Total | 500 |

From this hypothetical set:

- Decisive win rate: `320 / (320 + 130) = 71.1%`.
- Win percentage across all prompts: `320 / 500 = 64%`.
- Tie-adjusted score: `(320 + 0.5 × 50) / 500 = 69%`.

These are example calculations only and must not be presented as project results unless actually measured.

### 8.5 Don't rely on SpeechJudge alone

Using SpeechJudge to generate training preferences and then using it as the only final evaluator can overestimate improvement. The model may learn patterns that score well according to the judge without becoming more natural to humans.

The final report should also include:

- **Human blind A/B preferences:** a sample of people listen to the baseline and updated samples without being told which is which.
- **Text accuracy:** use ASR-derived word error rate or another appropriate metric, then manually inspect a subset because ASR has its own error modes.
- **Speaker similarity:** ensure naturalness training hasn't changed the speaker identity when preserving identity is a requirement.
- **Latency and reliability:** synthesis time, failures and output consistency, especially if the long-term use is in voice agents.
- **Uncertainty:** report the number of judgements, tie rate and preferably a confidence interval/bootstrapped interval for the preference result.

A statement such as “SpeechJudge preferred the updated model on 64% of all test prompts, with 10% ties” is honest and interpretable. It is not equivalent to saying “64% of humans prefer it.” Human-listener results should be reported separately.

### 8.6 Human-closeness score (decided benchmark metric)

SpeechJudge-Data contains no human recordings of the target sentences (both `audioA` and `audioB` are TTS outputs; humans only annotated preferences), so the human reference comes from **LibriTTS test-clean** (or LibriTTS-R), CC BY 4.0.

**Setup:**

- 10 speakers (5 male, 5 female) × 50 sentences = 500 sentences, 3–15 s each.
- For each speaker, 1–2 extra clips (same speaker, preferably same chapter, not among the 500) serve as the zero-shot voice-cloning prompt.
- Qwen TTS generates each sentence in that speaker's cloned voice, with fixed seed and settings. The model is `Qwen/Qwen3-TTS-12Hz-0.6B-Base` (Apache-2.0, voice clone, ships fine-tuning code): Qwen2.5-0.5B-TTS from the paper has no official public release (checked 2026-10-21).

**Judging:** SpeechJudge-GRM compares the TTS clip with the human clip for every sentence in both A/B orders (optionally several votes per order). Scores are parsed as numbers, not strings.

**Formula (decided):**

```
per-sentence closeness = mean TTS score / mean human score × 100
overall closeness      = mean of per-sentence closeness (also reported per speaker)
```

Example: human 9/10, TTS 6/10 → 66.7%.

**Known caveats to state in the report:** scores are pair-relative and on a 1–10 scale; SpeechJudge's 77–79% accuracy was measured on its A/B verdict, not on score magnitudes; values above 100% are possible when the judge prefers the TTS; a low-scored human clip can produce a large ratio. Report alongside WER, speaker similarity and UTMOS, and validate on a small blind human-listener subset.

Implementation: `scripts/run_benchmark.sh` runs `benchmark/prepare_data.py` → `generate_tts.py` → `judge.py` (formula) → `metrics.py`; see `README.md`.

## 9. Human role and AI-feedback training

### 9.1 Conventional RLHF

A simplified conventional RLHF loop is:

1. The model generates several responses.
2. Humans judge which are better.
3. Those preferences are used to train a reward model or otherwise construct a feedback signal.
4. The model is trained or optimized to improve the reward.
5. The model is evaluated and the cycle may repeat.

### 9.2 Turing Tester's AI-feedback variant

Turing Tester uses an existing SpeechJudge reward model that was trained on human-labelled preferences:

1. Qwen generates candidate speech.
2. SpeechJudge compares outputs or provides a reward signal.
3. The training algorithm turns that signal into a parameter update.
4. The updated Qwen generates new candidates.
5. The cycle repeats without requiring a human to compare every single iteration.

This is related to **RLAIF** (Reinforcement Learning from AI Feedback), although a particular implementation using DPO is technically preference optimization rather than policy-gradient RL.

### 9.3 Are humans eliminated?

No. Fresh human feedback can be reduced during the repeated optimization loop, but the judge's quality derives in part from prior human data. Humans also remain useful for:

- Validating whether the reward judge correlates with actual listener preferences.
- Evaluating out-of-distribution speech, languages and styles.
- Resolving cases where the judge is uncertain or its criteria conflict.
- Producing demonstrations or preferences for weaknesses missing from the existing dataset.
- Checking that training has not introduced undesirable trade-offs.

This is best understood as reusing and scaling prior human judgment, not eliminating humans from the system altogether.

## 10. Should the training set be 10,000–15,000 examples or should a bigger model be a teacher?

These are different strategies, not directly interchangeable.

### Option A: Use 10,000–15,000 preference/training conditions from existing data

This is the route recommended for the first online-DPO experiment, but only expand to that scale after profiling the pipeline. Start with a smaller pilot and see how much audio can be generated, how many judge calls are required, and how long optimization takes.

If using SpeechJudge-Data directly for offline DPO, use its human preferences and valid split. If using online DPO, select suitable text/reference conditions, generate new Qwen candidates, then use SpeechJudge to label the newly generated candidates.

### Option B: Use a larger teacher TTS model to generate demonstrations

A larger model can supply target audio for SFT, provided the audio is legally usable for model training and correctly matches the text, speaker reference and intended style. This does not directly replace preference optimization; it creates a different training signal.

For a fair research-style comparison, one could later test:

- Base Qwen.
- SFT on allowed teacher audio.
- Offline DPO on existing human preferences.
- Online DPO using SpeechJudge.
- SFT followed by DPO.

However, the hackathon plan is to choose **one main method**, not train all methods and then pick a winner. Online DPO with SpeechJudge is the selected main path because it best demonstrates the intended automated feedback loop and has a relevant precedent in the paper.

### Why not use ElevenLabs blindly as teacher?

The earlier discussion flagged that provider terms may restrict using generated outputs to train, fine-tune or improve other models unless such use is expressly allowed. Verify current terms and permissions before using any proprietary TTS provider's output as an SFT target. An open teacher or provider that explicitly permits the required use may be safer.

## 11. Data recommendation idea for a future iteration

The broader product concept includes a feature that tells a lab what additional data it needs to collect based on the model's weaknesses.

Potential future workflow:

1. Evaluate the model across different text types, speaking styles, languages and scenarios.
2. Group failures into categories supported by evidence.
3. Estimate where the model or reward judge has low confidence or inconsistent outcomes.
4. Recommend targeted examples, e.g. conversational emphasis, sentence-final intonation, longer turns, numbers/proper nouns, code-switching or a particular style.
5. Ask human listeners to compare candidates in those specific cases where additional judgment is valuable.
6. Add the reviewed examples to an appropriate training set and retrain/optimize.
7. Run the locked benchmark to check whether the targeted weakness improved without degrading other skills.

This should be presented as a future feature rather than a fully solved part of the hackathon prototype. SpeechJudge's explanations are not a validated data-acquisition policy, and the source dataset does not provide comprehensive timestamped defect labels. Additional validation and task-specific annotations may be required.

## 12. Proposed system architecture

A sensible first architecture is modular:

### Frontend/dashboard

- Upload audio or select a model/prompt set.
- Display baseline and trained audio players.
- Display scores, preferences, explanation and warnings.
- Show checkpoint/run history and benchmark results.
- Keep human evaluation results separate from automated grader results.

### Backend API

- Accept evaluation and training-run requests.
- Validate input text, audio and model identifiers.
- Store run metadata and generated outputs.
- Dispatch evaluation or training jobs.
- Serve aggregate benchmark results.

### SpeechJudge worker

- Load the pretrained SpeechJudge-GRM checkpoint.
- Decode/convert audio to its expected input format.
- Compare paired outputs using the documented interface.
- Return score, preference and explanation.
- Track evaluator version and inference settings.

### TTS generation worker

- Load base or current Qwen checkpoint.
- Generate audio from prompt/text/speaker-reference conditions.
- Save output audio plus generation metadata.
- Apply basic output validation.

### Preference construction and optimization

- Pair candidates generated for identical or compatible conditions.
- Use SpeechJudge to select preferred/rejected outputs.
- Filter invalid candidates or text-inaccurate examples.
- Construct DPO training examples using the TTS model's supported training format.
- Save training configuration and checkpoints.

### Benchmark worker

- Maintain a locked held-out prompt list.
- Generate from both base and trained checkpoints under fixed conditions.
- Compare pairs via SpeechJudge.
- Run ASR-based text accuracy and any suitable speaker-similarity measure.
- Store outcomes and calculate preference statistics.
- Export a report.

### Storage

At minimum, track:

- Prompt ID, input text and split designation.
- Speaker reference/voice/style information and source/usage permissions.
- Model and checkpoint version.
- Generation parameters and seeds where applicable.
- Audio file locations and metadata.
- SpeechJudge result, pair order, score, textual rationale and judge version.
- DPO pair records and training provenance.
- Benchmark measurements and human ratings.

Use access controls and clear data-retention rules. Do not treat user-provided model checkpoints or audio as safe to execute or expose without validation.

## 13. Hackathon plan and milestones

The order below minimizes risk. The team should not start with large-scale optimization before proving the evaluator works.

### Milestone 1 — Run the evaluator

- Clone the official SpeechJudge repo.
- Install its documented dependencies in an isolated environment.
- Download the current reward-model checkpoint.
- Run the official sample or `compare_wavs()` example.
- Understand the input format and what the scores and analysis mean.

**Exit criterion:** two sample audio files and the correct target text produce an evaluator result.

### Milestone 2 — Generate base-Qwen outputs

- Set up Qwen2.5-0.5B-TTS or the chosen supported TTS model.
- Generate a small set of recordings from fixed text prompts.
- Confirm repeatable, valid audio generation.
- Save the model identity, text and generation settings.

**Exit criterion:** produce a small paired set of candidate recordings reliably.

### Milestone 3 — Build pairwise grading

- Feed candidate pairs and the correct target text to SpeechJudge.
- Save preferences and explanations.
- Compare variants of the same prompt rather than unrelated recordings.
- Check whether text accuracy or quality differences make pairs incomparable.

**Exit criterion:** the system can rank candidate outputs and store the result.

### Milestone 4 — Implement a small online-DPO pilot

- Start with a very small number of prompts and candidates.
- Generate candidate pairs from the current model.
- Use SpeechJudge to select preferences.
- Feed those pairs to a compatible DPO training loop.
- Save a new checkpoint and verify it can generate audio.

**Exit criterion:** the model parameters were updated by the training algorithm; the prototype is not merely selecting an existing best sample.

### Milestone 5 — Lock the before/after benchmark

- Finalize about 500 test prompts before training/tuning decisions.
- Ensure they are not used in training and check duplicate prompt leakage.
- Generate base outputs and store them.
- Train Qwen using the separate training pool.
- Generate outputs from the updated Qwen on the same 500 prompts.
- Run paired SpeechJudge comparisons.
- Run text-accuracy and speaker-similarity checks where practical.
- Collect blind human preferences for a subset.

**Exit criterion:** a report compares base vs updated model using the exact same held-out prompts.

### Milestone 6 — Build the demo/report

Show:

1. A base-Qwen recording.
2. The SpeechJudge comparison/diagnostic result.
3. Evidence that a training update happened.
4. An updated-Qwen recording for the same text.
5. Before/after benchmark metrics, including ties and failures.
6. Clear labels that distinguish SpeechJudge preference from human preference.

**Exit criterion:** a judge can understand what changed, why it was changed, and what evidence supports the improvement.

### Stretch milestones

- Add diagnostic categories beyond the SpeechJudge pairwise output.
- Add a data-recommendation module.
- Add a supported external TTS endpoint for evaluation-only use.
- Add uncertainty/low-confidence routing to human review.
- Add SFT or a second preference-training approach after the main loop works.

## 14. Decisions made and recommended defaults

| Decision | Recommendation | Reason |
|---|---|---|
| Product category | TTS evaluation and improvement environment, not AI-vs-human detector | Matches the clarified product vision |
| Main judge | Reuse SpeechJudge-GRM | Avoids building a reward model from scratch |
| Initial TTS model | Qwen2.5-0.5B-TTS | Closest to the paper's downstream training experiment |
| Main training method | Online DPO using SpeechJudge preference/reward feedback | Demonstrates generated candidates → AI evaluation → parameter updates |
| Main data source | SpeechJudge resources, with training data and locked evaluation separated | It includes human preferences and a trained judge |
| First benchmark | Approximately 500 locked held-out prompts, same prompts before and after | Provides a paired comparison |
| Human evaluations | Blind A/B assessment on a subset | Guards against reward hacking and judge-specific overfitting |
| Main demo | Base output → evaluator feedback → trained checkpoint → before/after results | Makes the end-to-end product visible |
| Teacher SFT | Do not make it the principal method in the first demo | Requires compatible target audio and introduces more moving parts |
| Full policy-gradient RL | Stretch goal | More engineering risk than the online-DPO route |
| Training scale | Start small; scale toward 10K–15K training conditions only after profiling | Candidate generation and judge inference may dominate runtime |

## 15. Risks, failure modes and mitigations

### 15.1 Reward hacking

Qwen may learn to optimize quirks that SpeechJudge likes rather than generating speech people prefer.

**Mitigation:** human blind A/B tests, independent checks, text-accuracy constraints, multiple metrics, and auditing for systematic degradation.

### 15.2 SpeechJudge only compares relative quality

A comparison score does not automatically provide an absolute, calibrated score for one recording.

**Mitigation:** make pairwise comparison the core evaluation; if displaying a “score out of 100,” calibrate it against human judgments and label it as an estimate. Do not imply a calibrated absolute measure without validation.

### 15.3 Training data and benchmark leakage

If prompts in the benchmark also appear during training or model-selection, reported results can look better than true generalization.

**Mitigation:** lock the test set, track prompt IDs, deduplicate similar sentences, keep a separate validation set and do not repeatedly tune against the final test.

### 15.4 Naturalness vs intelligibility trade-offs

A voice may sound more expressive but say the wrong words. A reward model could prefer an output for naturalness even if it has transcription errors.

**Mitigation:** evaluate text fidelity separately, reject invalid candidates, and use appropriate constraints or multi-objective training.

### 15.5 Speaker identity drift

Training for naturalness could change the voice identity or make it less similar to a required reference.

**Mitigation:** track speaker similarity and include it in evaluation/constraints when identity preservation is required.

### 15.6 Judge bias, language coverage and style coverage

SpeechJudge's documented data focuses on English/Chinese, and model accuracy can vary with style and language. Do not assume reliable Hindi/Hinglish or every accent without validation.

**Mitigation:** frame the initial benchmark around supported/validated conditions, then gather and evaluate new language-specific human preference data.

### 15.7 Technical mismatch between SpeechJudge and TTS training

The judge can compare audio, but DPO requires a training pipeline compatible with the TTS model's actual output representation and probabilities. TTS architectures may generate speech tokens, acoustic tokens or use multiple stages.

**Mitigation:** verify the official model training pipeline first. Do not assume an ordinary text LLM DPO trainer can train the TTS model without adaptation.

### 15.8 Compute and runtime

The judge checkpoint is large. Candidate generation, reward inference and training can compete for GPU memory and time.

**Mitigation:** profile a tiny end-to-end batch first, consider separate inference and training jobs, and choose an appropriate cloud GPU or compatible quantization/offloading strategy. Avoid committing to a large run until throughput is known.

### 15.9 Licensing

SpeechJudge's public model and dataset are marked CC BY-NC 4.0. Other provider-generated audio may carry separate terms.

**Mitigation:** read the current licence and usage terms, document attribution, confirm the hackathon usage conditions, and obtain suitable permissions before commercial use.

## 16. How to explain the project to hackathon judges

### Short pitch

> **Turing Tester is a feedback-driven training environment for TTS models. It evaluates generated speech, uses a learned preference model to find better candidates, helps update supported TTS models through online preference optimization, and measures the result on locked tests. The goal is to replace manual trial-and-error with a repeatable process for making synthetic voices more natural without sacrificing text accuracy or voice identity.**

### What makes the project meaningful

- It does more than detect an issue; it integrates evaluation with training.
- It reuses a published learned reward model rather than pretending to build one from scratch.
- It supports an iterative loop in which the model's own candidates are judged and used for further optimization.
- It includes a repeatable benchmark rather than relying only on a hand-picked audio demo.
- It keeps human listening tests in the loop to check whether the reward judge reflects real preferences.

### Claims to avoid

Do not claim:

- That Turing Tester has invented reward-model-driven TTS optimization; the SpeechJudge paper already demonstrates a related post-training experiment.
- That it completely removes humans from RLHF; it reuses judgments learned from existing human feedback and still needs independent human validation.
- That a SpeechJudge score is an absolute “human-likeness percentage.”
- That an increase in the judge's score proves human listeners prefer the result.
- That DPO is synonymous with policy-gradient RL.
- That the system can directly update any commercial TTS API, regardless of provider support.
- That 500 test prompts prove universal improvement for all languages, voices and styles.

A strong, honest claim is that the prototype automates a TTS evaluation-to-preference-optimization loop and tests whether the new checkpoint improves on a fixed held-out benchmark.

## Final recommendation

For the hackathon, keep the first implementation narrow and complete:

1. Reuse SpeechJudge-GRM.
2. Use Qwen2.5-0.5B-TTS as the main TTS model if its training integration works in your environment.
3. Generate candidates for the same prompt and ask SpeechJudge to rank them.
4. Convert those preferences into a small online-DPO training update.
5. Run the original and updated Qwen on the same approximately 500 held-out prompts.
6. Report SpeechJudge win/loss/tie results, text accuracy, speaker consistency and independent human preferences where possible.
7. Demonstrate that the weights were actually updated and that the resulting audio was evaluated, rather than simply selecting a better sample.

Build the broader “what data does this model need?” and multi-model service after the core loop works. The strongest hackathon result will not be the number of features; it will be a clear, reproducible demonstration that an automated feedback signal helped improve a TTS model and that the improvement survives evaluation beyond the reward model that drove training.
